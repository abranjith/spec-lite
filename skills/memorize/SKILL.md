## Required Context

- Read `.spec-lite/memory.md` when present, `.spec-lite.json` for the project profile, and matching `.spec-lite/stacks/*.md` snippets for bootstrap.
- User edits to memory and stack snippets are intentional and take priority over bundled defaults.

## Modes

- `/memorize <instructions>`: add durable project-wide rules.
- `/memorize override <instructions>`: explicitly replace conflicting rules.
- `/memorize bootstrap`: synthesize initial prescriptive memory from profile, root manifests/config, and stack snippets.

Reject transient, feature-local, speculative, secret, or personal information. If memory is missing, create it.

## Add / Override Process

1. Parse each instruction's imperative intent and best standard section.
2. Scan every section for semantic overlap:
   - **Duplicate** (same rule): skip and report “Already memorized.”
   - **Near-duplicate** (same intent, different phrasing): show both and ask keep/adopt/merge.
   - **Conflict** (same topic, incompatible rule): show both and ask which to keep.
   - **Complementary**: add normally.
3. Resolve all near-duplicates/conflicts before any write; do not partially write. `/memorize override` replaces conflicts without another confirmation.
4. Append concise imperative entries to the best existing standard section. Create a standard section only when necessary; preserve unrelated order/content.
5. Re-scan the whole file after writing. Never leave duplicates or contradictions; surface any pre-existing conflict instead of silently choosing.
6. Report additions, skips, merges, overrides, and unresolved conflicts.

Semantic intent controls classification: “Use Pino” conflicts with “Use Winston,” while “Use Pino” complements “Log HTTP requests.”

## Memory Capture Protocol

Core agents and skills use this protocol at the end of their own task without a separate `/memorize` invocation. Memorize remains the authority on taxonomy, semantic deduplication, conflicts, and restructuring; protocol participants may append only qualifying entries.

### What Qualifies

- A durable, project-wide user instruction: explicit “always,” “never,” or “prefer” guidance; a stable style/process preference; or the same correction made twice.
- A codebase convention only when consistent, verified in multiple independent places, and absent from memory.
- Never task-local choices, guesses, temporary workarounds, secrets, personal data, or single-instance patterns.

### End-of-Task Procedure

1. Before What's Next, collect at most three candidates.
2. Scan all sections using the rules above. Skip duplicates; leave near-duplicates/conflicts unchanged and report them for user resolution. A conflict prevents partial writes that task.
3. Append each new rule under the best standard section as a concise imperative suffixed `*(auto-captured YYYY-MM-DD)*`.
4. Report every capture, or state that nothing qualified; the user may veto or revise it.

Only Memorize may reorder, merge, rename sections, clean the whole file, or replace conflicts. The writer set is Memorize plus roles explicitly following this protocol.

## Section Taxonomy

| Section | Contents |
|---|---|
| **General** | Cross-cutting preferences not fitting elsewhere |
| **Tech Stack** | Language/framework/runtime and key dependency roles |
| **Project Structure** | Layout, module, file naming conventions |
| **Coding Standards** | Naming, formatting, language idioms |
| **Architecture** | Structural principles and boundaries |
| **Design Patterns** | Project-specific patterns |
| **Error Handling** | Failure classification, propagation, response rules |
| **Logging** | Library, levels, fields, prohibited content |
| **Testing** | Framework, placement, naming, mocking, coverage |
| **Security** | Trust-boundary, auth, validation, secrets, PII rules |
| **Dependencies** | Package choices, versions, audit/update policies |
| **Documentation** | Documentation maintenance/conventions |
| **Performance** | Measurement and performance constraints |
| **Data Model** | Schema conventions and `.spec-lite/data_model.md` reference |

Prefer General over a one-entry custom section; never exceed 15 sections.

## Bootstrap

Bootstrap is lightweight and prescriptive; it does not scan source, trace imports, or claim implemented patterns.

1. Read `.spec-lite.json.projectProfile`; if absent, ask for languages, frameworks, tests, architecture, and explicit conventions.
2. Read only root manifests/configuration and one top-level directory listing. Extract actual versions, scripts, strict/lint/format/test configuration; do not recurse into source.
3. Read matching `.spec-lite/stacks/*.md`. User-edited/removed recommendations override bundled content.
4. When web access exists, verify time-sensitive practices using official language/framework/style documentation only; otherwise use the snippet and established knowledge.
5. Synthesize specific, actionable, grounded sections. Label architecture as recommended rather than observed.
6. Present assumptions and the proposed memory for user approval before writing.

Always include these user-overridable baselines under the indicated sections:

- **General**: Keep functions small, focused, and intention-revealing.
- **General**: Fail fast with clear, actionable messages.
- **General**: Remove dead or commented-out code instead of retaining it.
- **General**: Deduplicate shared logic; ask about backwards compatibility when unclear, and remove legacy behavior cleanly when not required.
- **Error Handling**: Never swallow exceptions; handle errors at boundaries and distinguish expected failures from unexpected faults.
- **Security**: Never hardcode secrets; use environment configuration or a secrets manager.
- **Security**: Validate and normalize input at trust boundaries.
- **Security**: Apply least privilege and parameterized database queries.
- **Testing**: Test observable behavior, keep tests deterministic, and cover edge/error paths.
- **Testing**: Follow stack-idiomatic naming/placement; ask before changing code for pre-existing failing tests.
- **Performance**: Measure before optimizing; prevent N+1 access and unbounded loads.
- **Dependencies**: Commit lockfiles, prefer stable/LTS releases, and audit known vulnerabilities.
- **Documentation**: Keep documentation synchronized with behavior changes.
- **Logging**: Use structured, level-appropriate logging and never log PII, secrets, or credentials.

If memory contains init seed markers, extract the seed as input, reconcile it with bootstrap (dedupe or ask on conflict), and remove markers only in the approved organized output. For organized memory, show a diff/summary and ask merge, replace, or cancel; never overwrite silently.

## Constraints

- Never silently drop, override, duplicate, or contradict instructions.
- Do not reorder user entries except for an approved merge/override/full cleanup.
- Bootstrap conventions must be supported by profile/config/snippets, not invented source analysis.
